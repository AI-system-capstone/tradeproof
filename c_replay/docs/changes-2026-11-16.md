# 검증 시작 방식 변경: B가 검증 Job을 만든다 (2026-11-16)

- 작성: C 강민성
- 관련 요구사항: VAL-01(골든셋 검증), VAL-02·03(Replay), UI-02(운영 화면)
- 관련 브랜치
  - `c/m3-validation-api`: 검증 등록 API 삭제, 멈춘 검증 정리 함수
  - `c/m3-validation-job`: 검증 Job 진입점·양식·이미지 (이 문서 포함). `c/m3-validation-api` 위에 쌓은 브랜치
  - `c/m8-admin-ui`: 운영 화면, 시연 화면

## 1. 왜 바꿨나

- B의 구현(PR #8, `b_registry/verify/replay.py`)이 이미 검증 Job을 직접 만든다.
  - 반입 검증을 통과한 번들(`validated`)마다 C의 Job 양식에 `BUNDLE_ID`를 넣어 K8s Job을 만든다.
  - C의 `POST /validations`는 부르지 않는다.
- 그런데 C는 "B가 `POST /validations`로 검증을 등록하고, Job은 `--validation-id`로 그 검증을 실행한다"를 전제로 만들어져 있었다.
  - 이 상태로는 B가 만든 Job이 C에서 바로 실패한다(인자 없음).
- 그래서 B의 방식에 C를 맞췄다. 검증 행은 Job이 직접 만들고, 등록 API는 없앴다.

## 2. 바뀐 처리 순서

```
B: 반입 검증 통과 → 번들 상태 validated
B: C의 Job 양식(job-template.json)에 BUNDLE_ID를 넣어 K8s Job 생성
K8s: C 검증 이미지로 파드 실행 → python -m c_replay.job
C Job: ① B의 GET /bundles/active 로 운영(기준) 번들 확인
       ② 검증 행 생성 (queued → running)
       ③ 골든셋 검증 + Replay
       ④ completed 또는 failed 로 저장
       ⑤ B에 완료 알림 POST
B: C의 GET /validations?bundle_id= 로 결과를 읽고 게이트 판정 → approved / rejected
```

- 용어 풀이
  - Job: 한 번 실행하고 끝나는 K8s 작업. 끝나면 성공·실패만 기록하고 다시 켜지 않는다.
  - Job 양식(템플릿): Job을 만들 때 쓰는 요청서. 이미지·명령·환경변수가 적혀 있고, B가 `BUNDLE_ID`만 채운다.
  - SIGTERM: 프로그램에 "종료하라"고 보내는 신호. K8s가 시간 제한을 넘긴 Job을 멈출 때 보낸다.

## 3. 바뀐 것

### 3-1. 검증 API는 조회만 한다 (`c/m3-validation-api`)

- `POST /validations`(검증 등록)를 삭제했다. 이제 보내면 405가 돌아온다.
- 등록 요청 형식(`ValidationRequest`), 요청자 헤더(`X-Actor`), 기준 번들 기본값 환경변수(`BUNDLE_ID`)도 삭제했다.
- 남은 API: `GET /validations`, `GET /validations/{id}`, `GET /validations/{id}/diffs`, `/admin`, `/healthz`, `/livez`, `/metrics`
- 명세(`docs/openapi/c_replay.json`)의 흐름 설명을 새 순서로 고쳤다.
- 테이블 구조는 그대로다. `requested_by` 칸의 설명만 바꿨다(B가 만든 Job이면 `b_registry`).

### 3-2. 검증 Job (`c/m3-validation-job`)

- 시작 방법
  - 전: `python -m c_replay.job --validation-id RP-...`
  - 후: `BUNDLE_ID=B-9 DATABASE_URL=... B_URL=... python -m c_replay.job`
- 환경변수

  | 이름 | 필수 | 내용 |
  |---|---|---|
  | `BUNDLE_ID` | 예 | 검증할 후보 번들. B가 채운다 |
  | `DATABASE_URL` | 예 | C의 검증 테이블 + A의 거래·판정·정답 테이블 |
  | `B_URL` | 아니오 | B 주소. 기준 번들 조회와 완료 알림에 쓴다. 없으면 기준 번들은 B-7, 알림은 보내지 않는다 |
  | `BLOB_*` | 아니오 | 업로드 원문 저장소 |

- 종료 코드: 0 = 완료, 1 = 실패 또는 시작 못 함, 2 = 필수 환경변수 없음
- 새로 생긴 동작
  - 기준 번들을 B의 `GET /bundles/active`에서 받는다.
  - 검증 행을 Job이 직접 만든다.
  - 끝나면 B에 완료 알림을 보낸다.
    - 경로: `POST {B_URL}/bundles/{bundle_id}/validation-results`
    - 내용: `{validation_id, bundle_id, status}`
    - 실패하면 1초, 2초 쉬고 다시 보낸다(최대 3번). 끝내 실패해도 결과는 C의 DB에 남아 있다.
    - **이 경로는 가정이다.** B가 받는 API를 아직 만들지 않았다.
  - 시간 제한에 걸려 SIGTERM을 받으면 `failed`로 저장하고 알림을 보낸다.
  - 오래 진행 중으로 남은 같은 번들의 검증은 시작할 때 `failed`로 정리한다(7-1).
  - B에 연결할 수 없으면 기준 번들을 비워 둔 채 `failed`(B 연결 불가)로 남긴다. 실패가 화면에 보이게 하려는 것이다.
  - 같은 번들의 검증이 진행 중이면 아무것도 하지 않고 끝난다(종료 코드 1).
- Job 양식 `c_replay/job/job-template.json` (새 파일)
  - B가 읽는 JSON 형식(`batch/v1` Job)
  - 재시도 없음(`backoffLimit: 0`), 시간 제한 3600초(`activeDeadlineSeconds`)
  - 환경변수는 Secret `tradeproof-env`에서 받고, `B_URL`은 `http://b-registry:8100`
  - **끝난 Job 자동 삭제 설정은 넣지 않았다.** 번들이 `validated`인 동안 Job이 지워지면 B가 다시 만든다.
- 이미지 `c_replay/Dockerfile`
  - `--target api`: 조회 API + 운영 화면 (`tradeproof/c-replay:dev`)
  - `--target job`: 검증 Job (`tradeproof/c-replay-job:dev`). tesseract를 A와 같은 버전(5.5.0)으로 고정하고 A의 OCR·판정 코드를 넣었다.
  - Job 파드에는 `/app/data`(제재 리스트·서류)를 붙여야 한다.

### 3-3. 운영 화면 (`c/m8-admin-ui`)

- 검증 결과를 실제 C API로 읽게 고쳤다.
  - 번들로 가장 최근 검증 찾기: `GET /validations?bundle_id=…&limit=1`
  - 결과 표시: 골든셋 지표(정확도·미탐·오탐), Replay 요약
  - 달라진 거래 표: `GET /validations/{id}/diffs`
- 예시 데이터(`?mock=1`)도 실제 응답 형식으로 바꿨다.
- B·D를 부르는 부분은 이 시점에는 가정이었고, 7-5에서 실제 API에 맞췄다.

## 7. 점검 뒤 고친 것

### 7-1. 멈춘 검증 정리 (해결: 위 6절의 SIGKILL 항목)

- Job이 검증 행을 만들기 전에, 같은 번들의 진행 중(queued·running) 검증 중 생성 후 4200초가 지난 것을 `failed`로 바꾼다.
  - 기준: Job 시간 제한 3600초 + 600초. 상수 `STALE_AFTER` 하나.
  - 더 최근 것은 진행 중으로 보고 건드리지 않는다. 이 경우 Job은 지금처럼 아무것도 하지 않고 끝난다.
  - 정리한 행의 에러: `INTERNAL`, "중단된 검증을 정리함 …".

### 7-2. Replay가 읽는 과거 기록

- `read_past`: 거래마다 한 줄만 읽는다.
  - Job이 있으면 그 Job의 번들로 처리한 기록. 없으면 가장 최근(`screened_at`, 같으면 `result_id`) 기록.
  - 처리 중(queued·processing) 거래는 전과 같이 뺀다.
- `replay_result`: 입력에 같은 `tx_id`가 있으면 `ValueError`.
- 이전 기록의 번들이 기준 번들과 다른 거래 수를 로그 한 줄(`past_bundle_mismatch`)로 남긴다. 화면에서는 `before.bundle_id`로 보인다.

### 7-3. 골든셋 한 건 실패

- 전체 실패는 유지한다. 일부로 센 정확도는 전체 정확도로 오해되기 때문이다.
- 실패 메시지에 거래 ID와 번들이 들어간다. 예: `GoldenFailed: 골든셋 TX-0002 처리 실패 (B-7): ValueError: …`

### 7-4. 종료 신호

- 검증 행을 만든 뒤에는 신호가 어느 지점에서 와도 `failed` 저장 후 알림을 보낸다.
- 이미 `completed`로 저장된 뒤라면 결과를 바꾸지 않는다.
- 알림 중에 신호가 오면 알림을 한 번 더 보낸다.
- 신호 처리기는 첫 신호만 처리한다. 이후 신호는 무시한다.
- 알림 요청 제한을 10초에서 5초로 줄였다. 알림 전체는 최대 18초(5초 x 3번 + 대기 3초)다. 종료 유예 30초는 그대로다.
- 검증 행을 만드는 도중(행이 생기기 전)에 신호가 오면 행이 없을 수 있다. 행이 생겼는데 확인하지 못한 경우는 7-1이 정리한다.

### 7-5. 운영 화면

- B 호출을 B의 실제 API에 맞췄다.
  - 반입 업로드: 필드 이름 `package`. 조회: 202(처리 중) 또는 200 `{status: APPROVED|REJECTED, reason, bundle_id}`.
  - 번들 조회: `BundleResult` 형식. 게이트 판정·배포 ID는 B가 주지 않아 "B 미제공"으로 표시한다.
  - 승인·반려: `POST /bundles/{id}/transitions` `{to: approved|rejected, actor, reason}`.
- D 호출은 필드(`weight` 등)만 맞췄다. 배포 ID는 B가 주지 않으므로 사용자가 입력한다.
- 반입 결과의 단계(`steps`) 표는 B에 없어서 뺐다.

## 8. 미탐·오탐 정의 변경, A의 pipeline 사용 (2026-11-17)

### 8-1. 미탐·오탐을 위험도 방향으로 센다

- 위험도 순서: 통과 후보 < 담당자 검토 < 고위험 보류
- 미탐: 기대보다 **낮게** 분류한 건. 보류→검토, 보류→통과, 검토→통과.
- 오탐: 기대보다 **높게** 분류한 건. 통과→검토, 통과→보류, 검토→보류.
- 전에는 "통과 후보로 나온 건"만 미탐으로 셌다. 보류→검토는 정확도만 낮추고 미탐에는 잡히지 않았다.
- 바꾼 이유 (A 확인)
  - 판정 규칙 rules-v3는 OCR이 불확실하면 통과가 아니라 검토로 보낸다.
  - 그래서 저하 모델(`model-v4`)은 "보류→통과"가 아니라 "보류→검토"로 나타난다(A 측정: 미탐 0, 보류→검토 3건).
  - 이 건을 미탐으로 세지 않으면 게이트가 "미탐 0건"을 기준으로 삼을 때 저하 모델이 통과한다(S5).
- 응답 필드(`false_negative`, `false_positive`)는 그대로다. 계산식과 명세 설명만 바뀌었다.
- Replay의 `changed_down`(위험도가 낮아진 거래)과 같은 기준이다.
- 알아 둘 점: "보류→검토"와 "보류→통과"가 같은 숫자로 묶인다. 둘을 따로 보려면 필드를 더 둬야 한다.
- 정의는 회의 안건(MTG-06)이다. 팀 확인이 필요하다.

### 8-2. OCR → 판정을 A의 `a_screening/pipeline.py`로 한다

- 전: A의 내부 함수 `worker.screen_job`을 불렀다.
- 후: A가 C용으로 공개한 `pipeline.extract_documents` + `pipeline.screen_extracted`를 부른다.
  - 둘을 이어 부르면 `pipeline.screen_documents`와 같다. 나눠 부르는 이유는 같은 거래·같은 모델의 OCR을 한 번만 하기 위해서다.
  - A의 평시 심사(ocr-worker)도 같은 함수를 쓴다(SVC-04).
- pipeline은 번들 구성을 dict로 받는다. 그래서 번들 구성을 B에서 읽게 바꿀 때 C의 `validate.bundle()` 한 곳만 고치면 된다.
  - 지금은 여전히 `contracts.BUNDLES`에서 읽는다. B가 만든 번들이 실패하는 문제는 그대로다.
- 서류 폴더 준비
  - 시드·sample 입력: `data/docs/<tx_id>/`
  - upload 입력: 원문 저장소에서 내려받는다. PDF 렌더링 때문에 이 준비만 A의 `worker.prepare_upload`를 쓴다.
