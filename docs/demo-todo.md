## A (지윤아): 샘플 심사 서비스

### A-1. 검증 Job이 모델 파일 위치를 찾지 못하는 문제 (수정 완료, PR 필요)

- **문제:** C 검증 Job이 B에서 번들 구성을 직접 읽은 뒤 A의 OCR 코드에 모델 ID만 넘깁니다. 그런데 A의 `registry.py`는 번들을 직접 조회했을 때만 모델 ZIP의 위치를 기억합니다. 그래서 검증 Job이 "model 'model-v3' 의 ZIP 위치를 모름" 오류로 실패합니다.
- **필요한 이유:** 이 오류가 있으면 모든 후보 번들의 검증이 실패합니다. 검증 결과가 없으면 B가 게이트를 판정할 수 없고, S4와 S5 시연이 모두 멈춥니다.
- **해결 방안:** `registry.py`가 모델이나 리스트의 ZIP 위치를 모를 때 B의 번들 목록(`GET /bundles`)에서 위치를 찾도록 고쳤습니다. 이 경우를 확인하는 테스트도 추가했습니다. A가 이 변경을 PR로 올리고 리뷰를 받으면 됩니다.
- **완료 기준:** main에서 만든 검증 Job 이미지로 S4 검증이 `completed`로 끝납니다.

### A-2. 시연 데이터 준비 단계를 스크립트로 채우기

- **문제:** `scripts/gen_data.sh`와 `scripts/reset_demo.sh`에는 단계 이름만 있고 실제 명령이 없습니다. 지금은 골든셋을 드라이브 ZIP으로 받아야 하고, 시연을 다시 하려면 사람이 DB를 손으로 비워야 합니다.
- **필요한 이유:** 리허설은 매번 같은 시작 상태에서 해야 결과를 비교할 수 있습니다. 한 번 쓴 반입 ZIP은 같은 환경에서 다시 쓸 수 없으므로, 처음 상태로 되돌리는 절차가 꼭 필요합니다.
- **해결 방안:** 합성 데이터를 만드는 코드가 A 폴더에 있으므로, A가 데이터 단계(데이터 생성, 과거 거래 적재, 골든셋 적재)를 채웁니다. 이 PR의 `scripts/demo_reset.sh`와 `scripts/demo_up.sh` 5단계를 그대로 옮겨 쓸 수 있습니다. 데이터 생성은 버전이 고정된 data-pipeline 이미지 안에서 돌려야 OCR 결과가 같게 나옵니다.
- **완료 기준:** 새 PC에서 스크립트만으로 만든 `data/`가 드라이브 ZIP과 같은 해시를 가집니다. 리셋 뒤 `golden_labels`가 100건이고 B-7만 운영 중입니다.

### A-3. 골든셋 임시 스키마 정리 (데이터 담당과 함께)

- **문제:** `golden_labels` 테이블의 정식 정의(`common/schema/15_dataset.sql`)가 아직 주석 상태입니다. 그래서 A의 임시 정의(`a_screening/db/golden_labels_tmp.sql`)를 따로 실행해야 테이블이 생깁니다.
- **필요한 이유:** DB를 새로 만들 때 이 단계를 빠뜨리면 C 검증 Job이 골든셋을 읽지 못해 실패합니다. 실제로 처음 DB를 띄웠을 때 테이블이 없었습니다.
- **해결 방안:** 데이터 담당이 정식 스키마를 확정할 때까지는 A의 임시 정의를 `common/schema/`에 넣어 DB 초기화 때 자동으로 만들어지게 하는 방법을 제안합니다. 정식 스키마가 나오면 그 정의로 바꿉니다.
- **완료 기준:** 빈 DB를 띄우기만 해도 `golden_labels` 테이블이 있습니다.

## B (박시우): 반입 검증·릴리스 관리

### B-1. 담당자 이름이 한글이면 배포 요청이 실패하는 문제

- **문제:** B는 승인을 받으면 D에게 배포를 요청하면서 담당자 이름을 HTTP 헤더(`X-Actor`)에 넣습니다. HTTP 헤더에는 ASCII 문자만 들어갈 수 있으므로, 이름이 한글이면 요청을 보내기 전에 `UnicodeEncodeError`가 납니다. 화면에는 `SERVICE_UNAVAILABLE: D deployment acceptance could not be confirmed`가 표시됩니다.
- **필요한 이유:** 팀원 모두 한글 이름을 쓰고, 운영 화면은 담당자 칸에 적은 이름을 그대로 보냅니다. 시연 중에 누구든 한글 이름을 넣으면 배포가 시작되지 않습니다.
- **해결 방안:** B가 헤더에 넣기 전에 이름을 인코딩(예: 퍼센트 인코딩)하거나, 헤더 대신 요청 본문의 `actor`만 쓰도록 D와 맞춥니다. C 화면에서도 허용하지 않는 문자를 미리 막을 수 있습니다.
- **완료 기준:** 담당자 칸에 "지윤아"를 넣고 승인해도 canary가 시작되고, 배포 기록에 이름이 그대로 남습니다.

### B-2. 배포 요청 실패 뒤 모든 배포가 막히는 문제

- **문제:** B는 배포 요청의 결과를 모르면 그 요청을 `pending`으로 남기고, 중복 배포를 막으려고 다시 보내지 않습니다. 그런데 요청이 D에 닿지도 못하고 실패한 경우(B-1처럼)에도 `pending`으로 남습니다. 그 뒤로는 그 번들의 승인이 `Deployment outcome is unknown; POST was not retried`로 끝나고, 다른 번들의 배포도 "확인 대기 중인 배포가 있음"으로 모두 거부됩니다.
- **필요한 이유:** 한 번의 실패로 전체 배포 경로가 영구히 멈춥니다. 시연 중에 이 상태가 되면 DB를 직접 고치거나 환경을 리셋해야만 이어 갈 수 있습니다.
- **해결 방안:** 요청을 보내기 전에 난 오류(인코딩 오류, 연결 거부 등)는 `pending`이 아니라 실패로 기록합니다. 결과를 정말 모르는 경우를 위해, 담당자가 확인한 뒤 막힌 요청을 풀 수 있는 API를 추가합니다.
- **완료 기준:** 배포 요청이 D에 닿지 못해도 다시 승인을 누르면 배포가 시작되고, 다른 번들의 배포도 막히지 않습니다.

### B-3. 검증 실행이 실패했을 때 다시 돌릴 방법이 없는 문제

- **문제:** 검증 Job이 게이트 불합격이 아니라 실행 자체의 오류로 `failed`가 되면, 그 후보를 다시 검증할 HTTP API가 없습니다. 재실행 함수(`ReleaseService.start`)는 코드에 있지만 외부로 노출되어 있지 않습니다.
- **필요한 이유:** 이미지 문제나 일시적인 장애로 검증이 실패하면, 원인을 고친 뒤에도 그 후보를 검증할 수 없습니다. 이번 점검에서도 A-1과 C-1 때문에 검증이 실패했고, 컨테이너 안에서 함수를 직접 불러서 다시 돌려야 했습니다.
- **해결 방안:** `POST /bundles/{id}/validations` 같은 재검증 API를 추가하고, 운영 화면에 "다시 검증" 버튼을 둡니다. 이미 진행 중인 Job이 있으면 거부하는 기존 규칙은 그대로 둡니다.
- **완료 기준:** 실행 실패로 끝난 후보를 화면에서 다시 검증할 수 있습니다.

### B-4. B 배포 파일 리뷰

- **문제:** 저장소에 B를 쿠버네티스에 올리는 파일이 없어서, 이번에 `d_platform/k8s/demo/b-registry.yaml`을 새로 만들었습니다. 이 파일에는 검증 Job을 만들 권한(RBAC), 신뢰 공개키, 검증 Job 양식, D 주소가 들어 있습니다.
- **필요한 이유:** B의 실행 설정(환경변수, 권한)은 B가 가장 잘 압니다. 설정이 틀리면 검증 Job이 생성되지 않거나 서명 검증이 실패합니다.
- **해결 방안:** B가 이 파일의 환경변수와 권한 범위가 맞는지 리뷰합니다.
- **완료 기준:** B가 승인한 파일로 k3s에서 반입부터 검증 Job 생성까지 동작합니다.

## C (강민성): 검증·운영 화면

### C-1. 검증 Job 이미지에 파일 하나가 빠진 문제 (수정 완료, 리뷰 필요)

- **문제:** PR #23 이후 A의 OCR 코드가 `a_screening/registry.py`를 import합니다. 그런데 `c_replay/Dockerfile`의 job 대상은 이 파일을 복사하지 않습니다. 그래서 검증 Job이 시작하자마자 `ImportError`로 실패합니다.
- **필요한 이유:** main 그대로 이미지를 만들면 모든 검증이 실패하므로, S4와 S5 시연을 할 수 없습니다.
- **해결 방안:** job 대상의 COPY 줄에 `a_screening/registry.py`를 추가했습니다. C가 리뷰하고 병합하면 됩니다.
- **완료 기준:** main에서 만든 `c-replay-job` 이미지로 검증이 끝까지 돕니다.

### C-2. 검증이 진행 중인지 화면에서 알 수 없는 문제

- **문제:** 검증이 도는 1~2분 동안 운영 화면에는 번들 상태 `candidate · 검증 전`과 검증 상태 `running`만 보입니다. 화면은 5초마다 자동으로 다시 조회하지만, 그 표시가 빈 태그라 눈에 보이지 않습니다.
- **필요한 이유:** 시연을 보는 사람은 시스템이 멈춘 것인지 일하는 중인지 알 수 없습니다. 실제로 점검 중에도 "진행 상황이 안 보인다"는 지적이 나왔습니다. 골든셋 100건을 전부 다시 처리한다는 점이 이 시나리오의 핵심이므로, 그 과정이 화면에 드러나야 합니다.
- **해결 방안:** 1단계로 화면에 "검증 중 · 골든셋·Replay 처리 중 · 경과 42초"처럼 문구와 경과 시간을 표시하고, `queued`·`running`에 한글 풀이를 붙입니다. 2단계로 검증 Job이 처리 건수(예: 골든셋 37/200)를 `validations` 테이블에 주기적으로 기록하고, C API가 이를 돌려주면 화면이 진행 막대를 그립니다. 2단계는 DB 스키마가 바뀌므로 `docs/interfaces.md`에 기록해야 합니다.
- **완료 기준:** 검증 중인 번들을 조회하면 진행 중이라는 문구와 경과 시간(가능하면 처리 건수)이 보입니다.

### C-3. 지금 무엇이 운영 중인지, 롤백 뒤 무엇으로 돌아갔는지 안 보이는 문제

- **문제:** 운영 화면에 현재 운영(active) 번들과 canary 번들을 보여 주는 곳이 없습니다. 롤백을 해도 결과가 표(`status rolled_back`, `previous_bundle_id B-7`)로만 나오고, 배포 진행도 조회 버튼을 눌러야만 갱신됩니다.
- **필요한 이유:** S4의 핵심 장면은 "canary가 10 → 50 → 100으로 올라가고, 문제가 있으면 이전 번들로 돌아간다"입니다. 이 변화가 화면에서 바로 보이지 않으면 시연의 요점이 전달되지 않습니다.
- **해결 방안:** 화면 맨 위에 "운영 중: B-7 (model-v3 · list-v14) | canary: B-12 50%" 같은 상태 줄을 두고 5초마다 갱신합니다. 데이터는 이미 C 중계(`GET /api/b/bundles/active`)로 받을 수 있습니다. 롤백이 끝나면 "B-12 롤백 완료 → 운영 B-7로 복귀"라는 문구를 띄우고, 배포 칸은 진행 중일 때 자동으로 다시 조회합니다.
- **완료 기준:** 승인부터 롤백까지 버튼을 따로 누르지 않아도 상태 줄과 배포 칸에서 변화가 보입니다.

### C-4. 취소된 번들에서 승인하면 "승인됨"으로 보이는 문제

- **문제:** 이미 `cancelled`가 된 번들에서 "승인"을 누르면, B가 예전 배포 ID를 돌려주고 화면은 "승인됨 배포 요청함"이라고 표시합니다. 실제로는 아무 배포도 일어나지 않습니다.
- **필요한 이유:** 시연 중에 잘못된 성공 메시지를 보면, 진행자와 청중 모두 배포가 시작된 것으로 오해합니다.
- **해결 방안:** 번들 상태가 `validated`가 아니면 승인 버튼을 비활성화하고, 응답의 번들 상태가 `canary`가 아니면 "배포가 시작되지 않음"으로 표시합니다.
- **완료 기준:** 취소된 번들에서는 승인 버튼을 누를 수 없거나, 눌러도 실패로 표시됩니다.

## D (최은호): 배포·모니터링·인프라

### D-1. 시연 키트 배포 파일과 스크립트 리뷰·정식화

- **문제:** B와 C를 쿠버네티스에 올리는 파일, 그리고 시연 환경을 한 번에 올리는 스크립트가 저장소에 없었습니다. 이 PR에서 `d_platform/k8s/demo/`와 `scripts/demo_*.sh`를 새로 만들었습니다.
- **필요한 이유:** 팀원 모두가 같은 시연 환경을 같은 방법으로 올려야 리허설 결과를 비교할 수 있습니다. `scripts/`와 `d_platform/`은 D 담당 폴더이므로 D의 확인이 필요합니다.
- **해결 방안:** D가 이 파일들을 리뷰하고, 정식 위치와 이름을 정합니다. 이 키트는 D의 기존 구성(k3s, ingress-nginx, Argo Rollouts, `k3s_data_up.sh`, A 차트)을 그대로 씁니다.
- **완료 기준:** 새 PC에서 runbook만 보고 `scripts/demo_up.sh`로 시연 환경이 올라갑니다.

### D-2. 지표를 보고 스스로 롤백하는 기능이 없는 문제

- **문제:** A 차트의 canary에는 감시(AnalysisTemplate)가 아직 없습니다. 그래서 롤백은 사람이 운영 화면의 버튼이나 D API로 직접 해야 합니다. 롤백을 실행하는 경로 자체는 정상으로 동작합니다 (0.4초 응답, 약 8초 안에 이전 번들로 복귀).
- **필요한 이유:** S4의 목표는 "반영 후 감시하다가 이상하면 자동으로 되돌리는 것"입니다(MON-02). 사람이 누르는 롤백만으로는 이 요구사항을 보여 줄 수 없습니다.
- **해결 방안:** A가 내보내는 지표(`tradeproof_screening_failed_total`, `tradeproof_ocr_confidence_avg` 등, `bundle_id` 라벨 포함)를 기준으로 AnalysisTemplate을 만들어 canary 단계마다 검사합니다. 기준을 넘으면 Argo가 canary를 중단하고, D의 "밖에서 중단됨" 경로가 이를 감지해 롤백을 기록합니다. 시연용으로는 일부러 지표를 나쁘게 만드는 방법(예: `FAKE_FAIL_BUNDLES`와 같은 장치)도 필요합니다.
- **완료 기준:** 나쁜 지표를 내는 번들을 배포하면 사람이 누르지 않아도 canary가 멈추고 이전 번들로 돌아갑니다.

### D-3. D 배포 API를 클러스터 안에서 띄우기

- **문제:** D 배포 API는 지금 클러스터 밖(호스트)에서 kubeconfig로 실행됩니다. 그래서 PC를 재시작하거나 터미널이 끊기면 D가 꺼지고, B는 `host.k3d.internal`이라는 특수 주소로 D를 불러야 합니다.
- **필요한 이유:** 시연 직전에 D가 꺼져 있으면 승인이 실패합니다. 실제로 점검 중에 세션이 끊기면서 D와 포트포워드가 꺼져 화면이 열리지 않은 적이 있습니다.
- **해결 방안:** D 이미지에 `helm`, `kubectl`, Argo Rollouts 플러그인, 차트를 넣고, Rollout·Ingress·Secret 권한(RBAC)을 주어 클러스터 안에서 실행합니다(README의 TODO). 번들 값 파일은 볼륨이나 ConfigMap에 둡니다.
- **완료 기준:** 클러스터만 켜면 D 배포 API가 함께 뜨고, B와 C가 `http://d-platform:8300`으로 부릅니다.

### D-4. A 차트에 샘플 서류 폴더 마운트

- **문제:** A 차트는 `data/docs`를 마운트하지 않습니다. 그래서 클러스터에서는 "샘플 ID로 접수"가 `NOT_FOUND`로 실패하고, 서류 파일을 직접 업로드해야만 심사할 수 있습니다.
- **필요한 이유:** 검토 화면(A) 시연에서 샘플 거래를 바로 넣을 수 있어야 진행이 빠릅니다.
- **해결 방안:** 차트 values에 선택적인 볼륨 설정(`api.volumes`, `worker.volumes`)을 추가하고, 시연 키트에서는 노드의 `/data/tradeproof/docs`를 읽기 전용으로 마운트합니다.
- **완료 기준:** 클러스터에서 `POST /screenings {"sample_tx_id": "TX-0001"}`이 성공합니다.
