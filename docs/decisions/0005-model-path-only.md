# 0005 모델(OCR) 갱신 경로만 구현, 제재 리스트는 고정 한 버전
- 날짜 / 결정한 사람: 2026-11-12 / 멘토 피드백 반영 (시나리오 세부는 팀 확정 전 — 확정되면 이 파일을 고친다)
- 결정:
  - **0004(1차는 리스트 갱신만)를 대체한다.** 1차/2차 구분을 없애고, 11/22 기능 동결까지 모델 갱신 경로를 끝까지 구축하는 것을 1순위로 한다.
  - 제재 리스트 **갱신** 경로는 범위에서 뺀다: 리스트 반입, 리스트 Replay, 리스트 전면 반영(DEP-02), 리스트 버전별 골든셋은 하지 않는다.
  - 제재 리스트는 **고정된 한 버전**을 심사에 그대로 쓴다(매칭에 필요하므로 데이터로는 남는다). 골든셋도 그 리스트 기준 **하나**다.
  - 번들 개념은 유지한다. 실질은 "모델 버전 + 고정 리스트"다.
  - **지금은 정상 모델 하나만 만들어 S4·S6을 끝까지 구축한다.** 성능 저하·변조·손상 모델이 필요한 S1·S5는 시간이 남으면 추가한다. (번호는 그대로 둔다)
    - S4 (지금) 정상 개선 모델 → 골든셋·Replay 검증 → 게이트(자동 배포 또는 승인) → canary 10→50→100, 감시 지표가 기준을 넘으면 자동 롤백 (D, 검증·게이트 C)
    - S6 (지금) 모델 갱신 후 과거 거래를 당시 번들(모델)로 재처리 → 기록된 판정과 일치 (C)
    - S1 (시간이 남으면) 변조·손상 **모델 파일** 반입 → 서명·해시 검증 실패로 등록 전 차단 (B)
    - S5 (시간이 남으면) 성능 저하 모델 → 반입은 통과, 골든셋 기준 미달로 게이트 차단, canary 미실행 (C)
    - S2·S3 삭제. 승인 요청·반려 흐름은 S4의 게이트 안에, 자동 복구는 S4 canary의 자동 롤백으로 남는다.
  - 파인튜닝은 계획·코드에 넣지 않는다.
- 그대로 유지: 0001(SeaweedFS를 `minio:9000`으로), 0002(감사 기록 제외), 거래마다 `bundle_id` 기록, 옛 모델 파일 삭제 금지, 번들 교체는 Argo Rollout + `BUNDLE_ID`, `deploy/values-dev.yaml` → Helm → A의 `BUNDLE_ID`, 롤백 알림 → B 전이 API, B의 검증 통과 전이 → C의 Replay Job.
- 이유와 대안: 남은 기간(11/22 동결)에 두 경로를 모두 만들면 어느 쪽도 끝까지 못 갈 위험이 크다. 모델 경로 하나가 반입→검증→게이트→canary→감시·롤백→재현을 전부 관통한다. 대안이던 "리스트 먼저(0004)"는 canary·재현을 뒤로 미뤄 위험이 컸다.
- 영향: 모델 Replay는 과거 거래를 OCR부터 다시 처리하므로 무겁다 → 과거 거래 100건 이하, 필요하면 Indexed Job 병렬화(D 템플릿).
