# 0005 모델(OCR) 갱신 경로를 먼저, 제재 리스트 갱신은 이어서
- 날짜 / 결정한 사람: 2026-11-12 / 멘토 피드백 반영 (시나리오 세부는 팀 확정 전 — 확정되면 이 파일을 고친다)
- 결정:
  - **0004(1차는 리스트 갱신만)의 순서를 뒤집는다.** 리스트를 범위에서 빼는 것이 아니라 **우선순위를 미룬다.**
  - 1순위: **정상 모델 하나로 모델 갱신 경로를 끝까지 구축한다 (S4·S6).**
    - S4 정상 개선 모델 → 골든셋·Replay 검증 → 게이트(자동 배포 또는 승인) → canary 10→50→100, 감시 지표가 기준을 넘으면 자동 롤백 (D, 검증·게이트 C)
    - S6 모델 갱신 후 과거 거래를 당시 번들(모델)로 재처리 → 기록된 판정과 일치 (C)
  - 2순위: **모델 변형 시나리오** — 변조·손상 모델 파일 차단(S1), 성능 저하 모델 게이트 차단(S5)
  - 3순위: **제재 리스트 갱신 경로** — 리스트 반입, 리스트 Replay, 리스트 전면 반영(DEP-02), 리스트 버전별 골든셋 (S2·S3, S1의 리스트 쪽)
  - 모델 경로를 만드는 동안 제재 리스트는 **최초 번들의 한 버전**을 그대로 쓰고, 골든셋도 그 리스트 기준 하나만 둔다.
  - 번들은 계속 "모델 + 리스트" 묶음이다. 리스트를 이어서 붙일 수 있게 0004의 "처음부터 지킬 설계"를 그대로 지킨다.
  - 파인튜닝은 계획·코드에 넣지 않는다.
- 그대로 유지: 0001(SeaweedFS를 `minio:9000`으로), 0002(감사 기록 제외), 0003(S1~S6), 거래마다 `bundle_id` 기록, 옛 번들 파일 삭제 금지, 번들 교체는 Argo Rollout + `BUNDLE_ID`, `deploy/values-dev.yaml` → Helm → A의 `BUNDLE_ID`, 롤백 알림 → B 전이 API, B의 검증 통과 전이 → C의 Replay Job.
- 이유와 대안: 모델 경로 하나가 반입→검증→게이트→canary→감시·롤백→재현을 전부 관통하고, 가장 어려운 부분(canary·재현)을 먼저 확인할 수 있다. "리스트 먼저(0004)"는 canary·재현을 뒤로 미뤄 위험이 컸다.
- 영향: 모델 Replay는 과거 거래를 OCR부터 다시 처리하므로 무겁다 → 과거 거래 100건 이하, 필요하면 Indexed Job 병렬화(D 템플릿).
